# 工具箱（Toolbox）设计稿

> 本文是 2026-10-02 一轮 grilling 的产物。所有取舍都已在对话中由用户逐条确认，
> 标注「⚠ 已实测」的结论来自本机探针，不来自推测。

## 一句话

在**控制台**里新增一栏「工具」，把日常运营与开发用的小工具（JSON 格式化、二维码生成、
编码/摘要、时间戳、文本处理、标识与随机）做成**纯计算、无磁盘副作用**的工作区，
工具与「应用 / 分组」完全不联动。

---

## 1. 定位与边界

| 维度 | 决定 |
|---|---|
| 归属 | 控制台**新增一栏**，与分组管理并列；覆盖层不动 |
| 状态 | 工具**不写入** `AppBoxConfig`，**不进** `schemaVersion`，**不参与**方案导入导出与备份 |
| 生命期 | 输入与参数保留在内存：切工具、关控制台窗口都不丢；**退出进程才忘** |
| 联动 | 工具**读不到**当前选中的分组 / 应用，是独立小页面 |
| 磁盘 | 工具不读写任何应用文件、不动磁盘上的 app 包；唯一写盘动作是用户显式点击「导出 PNG」 |

> ⚠ 需要记账：ADR-0004 写的是「控制台只管理展示层」。工具与展示层无关，
> 因此**新增 ADR-0007** 记录这条边界，**不改写 0004**（已生效的决策记录不篡改）。
> ADR-0007 需要写清三件事：工具不做展示层之外的事、工具不碰配置与应用文件、
> 工具的能力上限（见第 5 节的正则约束）。

## 2. 界面结构

### 2.1 选中项

`ConsoleSelection` 是 enum（不是字符串），加一个 case：

```swift
public enum ConsoleSelection: Hashable, Sendable {
    case group(String)
    case missing
    case tool(ToolIdentifier)   // 新增
}
```

工具本身用 enum 而不是 String：12 个工具是**编译期已知的固定集合**，
用 enum 可穷尽、可测，也避免「侧栏里冒出一个 id 对不上任何工具」的空洞。

### 2.2 左栏

- 新增 `Section("工具")`，**平铺 12 行，不加分类小标题**（已定）。
- 底栏 `addGroupBar`（新建分组 + 开机启动）在 `selection == .tool` 时**隐去**——
  它描述的是分组与全局设置，工具态下没有意义。
- 「维护 → 失效应用」Section 的显隐规则不变。

### 2.3 右栏工作区

```
宽 ≥ 阈值            窄 < 阈值
┌────────┬────────┐  ┌────────────┐
│ 输入区  │ 输出区  │  │   输入区    │
│        │        │  ├────────────┤
│        │        │  │   输出区    │
└────────┴────────┘  └────────────┘
```

**自适应**：宽窗口左右分栏，窄窗口堆叠成上输入下输出。
12 个工具共用这一套骨架，各工具只提供「输入控件」与「输出控件」。
二维码这类图像输出在窄窗口下自动改用合适尺寸，不横向溢出。

### 2.4 状态归属

新增**独立的 `ToolboxModel`**，挂在 `ConsoleWindowController` 上（与 `ConsoleModel` 平级）。

- 工具态**不能**放 `@State`：右栏是 `if case .missing / else if let group` 分支出来的，
  切换选中项时 SwiftUI 可能重建子树，`@State` 随之蒸发——与「切工具不丢输入」直接冲突。
- 工具态**不塞进 `ConsoleModel`**：它已 388 行、职责是应用与分组，
  且 `apply(snapshot)` 里的 `isAvailable` / `isListed` 规则会误伤工具态。

### 2.5 ⚠ 与目录同步的冲突（必须刻意处理）

`ConsoleModel.apply(snapshot)` 现在会在 FSEvents 推送快照时校验
`isAvailable(selection, in: snapshot)`，选中项失效就落回「未分类」。
加了 `.tool` 之后，**正在用工具的人可能被一次目录变更踢回分组列表**。

处理规则：`isAvailable` 对 `.tool` **恒为 true**（工具不依赖磁盘，永远有效），
不得落回分组。这条要有单测盯住，不能靠编译器穷尽性检查蒙过去。

## 3. 计算模型

### 3.1 主线程永不跑工具逻辑

工具计算跑在后台，结果回主线程。UI 在任何输入下都不冻结。

### 3.2 预算 + 取消（诚实版）

⚠ 已实测：`NSRegularExpression` **没有步数上限，也无法从外部中断**。
`^(a+)+$` 的耗时是指数增长（n=20 → 0.038s，n=24 → 0.605s）。

因此「取消」的语义必须写准：**放弃等待，不是中断**。
到点的任务会被丢弃、UI 解除忙碌，但那个后台线程会继续跑到自然结束。
设计里不得暗示"可中断"。

每个工具声明自己的预算（输入长度上限 + 墙钟超时）；超限即提示"输入过大 / 回溯过深"，
不显示半成品结果。

## 4. 分层与可测性

沿仓库既有的**端口模式**（对照 `IconProviding` / `IconRendering`）：

```
AppBoxCore
  ├── 工具纯逻辑（可单测）：文本级 JSON 重排、Base64/URL 编解码、
  │   CryptoKit 摘要、时间戳换算、diff、转义、UUID/随机
  └── 端口 protocol：二维码位图渲染、时间取 "now"（供测试注入固定时钟）
        ↓ 外层注入真实实现
AppBox
  └── CoreImage（CIFilter.qrCodeGenerator）+ ImageIO 实现渲染端口
```

- ⚠ 已实测：`CIFilter.qrCodeGenerator` 属 CoreImage，**不依赖 AppKit**，能出图并写 PNG。
- ⚠ 但仓库现有惯例是 `AppBoxCore` **零系统框架**（19 个文件只 import Foundation + Observation）。
  把 CoreImage 直接拖进 Core 会破坏这条惯例、也让测试环境需要一个 CoreImage 运行时。
  所以走端口：**Core 定义端口，AppBox 注入实现**，两边惯例都不破。

## 5. 首批 12 个工具与各自的能力上限

| # | 工具 | 实现要点 |
|---|---|---|
| 1 | **JSON 格式化 / 压缩** | **文本级**重排（见 5.1）。错误提示用行列号 |
| 2 | **二维码生成** | 解码文本，纠错级别 L/M/Q/H + 尺寸可调；可复制图像或导出 PNG |
| 3 | Base64 编解码 | 支持 URL-safe 变体、换行忽略 |
| 4 | URL 编解码 | query 组件级编解码 |
| 5 | 哈希摘要 | MD5 / SHA1 / SHA256（CryptoKit，零 AppKit） |
| 6 | 时间戳 ↔ 日期 | 秒 / 毫秒切换、多时区、ISO8601 |
| 7 | 文本 diff | 标准库 `CollectionDifference`（Myers），**行级**需自行切分 |
| 8 | 正则测试 / 替换 | ⚠ 见 5.2，是全批唯一会锁死 UI 的工具 |
| 9 | JSON 转义 / 去转义 | 纯字符串变换，不走 `JSONSerialization` |
| 10 | UUID / ULID 生成 | 批量生成、大小写、无连字符选项 |
| 11 | 随机密码 | 长度 + 字符集开关 |
| 12 | 占位文本 | 段落 / 句子 / 单词 |

### 5.1 JSON 工具：为什么必须走文本级

⚠ 已实测（`JSONSerialization` 往返）：

| 输入 | 结果 |
|---|---|
| 键序 `zebra,alpha,mid,url,big,cn` | 输出 `cn,mid,alpha,url,big,zebra`（`NSDictionary` 哈希序，20 次稳定复现） |
| `"https://a.com/b"` | 写成 `"https:\/\/a.com/b"`（斜杠被转义） |
| 23 / 30 位整数 | ✓ 原样保住 |
| 44 位整数 | ✗ 变 `…99000000`（Double 精度） |
| `0.1` | ✗ 字面变 `0.10000000000000001` |
| `1e10` | ✗ 字面变 `10000000000` |

**所以：格式化只做缩进、换行、去尾随空格，不经过 `JSONSerialization` 的数字路径。**
键序原样、数字字面原样、斜杠不转义、大整数不丢。压缩（minify）天然是文本级操作。

错误定位仍用 `JSONSerialization` 的报错——它自带行列号，
实测形如 `Invalid value around line 3, column 7.`、`Number with leading zero around line 1, column 7.`。
⚠ 但这是从 `NSError.NSDebugDescription` 抠出的英文自由文本，格式无保证，
需要一层容错解析：**正则抠不出行列号时只显示原始信息，不吞错**。

### 5.2 正则：能力上限写在设计里

- 保留 `NSRegularExpression`。
- 输入长度上限 + 墙钟超时；超时作废并提示，不显示半成品。
- **不做**"静态拒绝危险 pattern"——嵌套量词/反向引用的合法用途太多，误伤比保护更烦人。
- **不做**自写无回溯引擎（成本与 bug 风险都不值）。

## 6. 验收标准

1. 工具**不产生**任何 `AppBoxConfig` 字段：`schemaVersion` 仍为 2，配置 JSON 里找不到工具痕迹。
2. 切工具、关控制台窗口、重开控制台 → 输入与参数仍在；`⌘Q` 退出后不再保留。
3. 工具态下，FSEvents 推送快照**不会**把选中项踢回分组列表（有单测）。
4. 工具态下底栏「新建分组 / 开机启动」隐去。
5. 输入一个带回溯的正则（如 `^(a+)+$` 配长输入）→ UI 不冻结，超时后给出提示。
6. 粘贴 44 位整数与大整数 JSON → 格式化输出**逐字节**保留原数字字面量与键序。
7. 二维码：中文/emoji/长 URL 都能出图；纠错级别与尺寸改变后产物随之改变。
8. `AppBoxCore` 仍**不 import** CoreImage / AppKit（有检查手段）。
9. 现有 291 个测试仍全绿；工具纯逻辑有新增单测。
10. **深嵌套输入不崩溃**：解析器对嵌套深度有上限，且该上限在**真实执行路径**
    （`ToolWork` 的 `DispatchQueue.global`，实测 524 KB 栈）上验证过，不是只在主线程上验证。
    有回归测试直接跑在 global 队列上。

## 附录：实现阶段实测纠正的假设

设计稿写完后，实现阶段用探针实测推翻了三条当时凭推理写下的判断。记在这里，因为它们比结论本身更能防住同类错误：

| 当时的说法 | 实测结果 | 后果 |
|---|---|---|
| 「`JSONSerialization` 会丢大整数精度」 | 23 / 30 位整数**原样保住**，44 位才失守 | 事实成立但被我夸大了；真正的问题是**键序被重排**与**斜杠被转义** |
| 「`maximumDepth = 500` 留了 2 倍余量」 | 主线程 500 层通过，但 `DispatchQueue.global`（工具实际执行处，524 KB 栈）**140 层就崩** | 上限在真实路径上提前 4 倍越界；改为 100，并加 global 队列回归测试 |
| 「`CIQRCodeGenerator` 输出就是纯模块矩阵」 | 输出**自带 1 模块静区**（版本 1 得到 23×23 而非 21×21） | 不扣掉它，界面上的静区数字与产物不符（设 4 得到 5）——「界面不说谎」不能容忍 |

贯穿三条的同一个教训：**用主线程的行为去推断其他执行上下文是危险的**，无论是栈大小还是 API 的隐含行为，都要在实际使用它的地方测。

## 7. 未决 / 后续切片

- 工具是否要支持"最近使用排序"（动到了「无状态」边界，先不做）。
- 二维码从图片识别（Vision）——需处理拖入文件与权限，后置。
- 正则替换的**批量文件**能力——一旦涉及写文件就跨过了 ADR-0007 的边界，需重新立项。
