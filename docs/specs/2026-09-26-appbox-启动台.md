# AppBox — macOS 启动台

日期：2026-09-26
状态：已对齐，待拆分为任务
上游：`CONTEXT.md`、`docs/adr/0001` ~ `0006`

## 1. 问题陈述

macOS 26 (Tahoe) 移除了系统自带的 Launchpad，取而代之的是 Spotlight 里的「Apps」视图。后者只能平铺列出所有应用，**无法把应用归纳成自定义分组**，也没有一个地方能对单个应用做展示层的调整（改名、隐藏、固定位置）。

结果是：应用装得越多，越难快速找到并启动目标应用；用户被迫依赖 Spotlight 的模糊搜索，失去了「一眼看到我的应用被组织成什么样」的能力。

AppBox 补上这个缺口：一个全屏启动台 + 一个管理控制台。

## 2. 方案概述

一个常规 macOS 应用（保留 Dock 图标），常驻后台并注册全局热键。它提供两个界面：

- **覆盖层**：由全局热键唤起、铺满鼠标所在屏幕、盖住所有窗口的启动台主界面。只负责浏览与启动。
- **控制台**：独立常规窗口，是配置的唯一写入场所。负责分组管理、单应用管理、全局设置、配置备份与方案切换。

应用以 bundleID 为主键被识别，配置以 JSON 文件持久化。AppBox 只管理**展示层**——分组、别名、隐藏、排序——绝不修改或删除磁盘上的应用文件。

## 3. 模块与接缝

目标是把全部领域逻辑关进一个不依赖 UI 的模块里，让测试有一个持久的靶心。

```
AppBoxCore   （SwiftPM library，不依赖 AppKit）
  ├── 领域模型        Application / Group / Library / Alias / Hidden / Missing
  ├── LibraryService  唯一门面：快照查询 + 全部变更操作
  ├── 持久化          JSON 编解码、schema 版本迁移、方案管理
  ├── 搜索            多字段匹配 + 拼音首字母
  └── 端口（protocol）AppScanning / IconProviding / Launching / Watching
                         ↓ 由外层注入真实实现，测试注入假实现
AppBox       （SwiftPM executable，SwiftUI + AppKit）
  ├── 覆盖层窗口      全屏 NSWindow、层级、焦点、多屏判定
  ├── 全局热键        Carbon RegisterEventHotKey
  ├── 系统实现        FileManager 扫描 / NSWorkspace 图标与启动 / FSEvents 监听
  └── 控制台 UI       SwiftUI 视图，全部通过 LibraryService 读写
```

**测试只打 `LibraryService` 这一个接缝。** 扫描、图标、启动、文件监听都是注入的端口，测试用假实现替换，因此全部领域测试不需要 AppKit、不需要真实 UI、不需要真实文件系统。

## 4. 用户故事

### A. 应用发现与同步

| 编号 | 行为 |
|---|---|
| A1 | 扫描 `/Applications`、`/System/Applications`、`~/Applications` 及其一级子目录，找出其中的 `.app` |
| A2 | 忽略应用包内部的嵌套 `.app`（如 `X.app/Contents/...`），避免把 Helper 当成应用 |
| A3 | 每个应用以 bundleID 为主键记录；极少数没有 bundleID 的应用，以绝对路径为主键 |
| A4 | 同一 bundleID 出现多个副本时只保留一个，优先级 `/Applications` > `/System/Applications` > `~/Applications` |
| A5 | 新发现的应用自动归入「未分类」组 |
| A6 | 配置中有、磁盘上找不到的应用被标记为「失效」：配置保留，不出现在覆盖层，在控制台中可查看 |
| A7 | 目录内容变化后（新装/卸载应用），下次唤起覆盖层时即反映变化，无需重启 AppBox |
| A8 | 「最近已知路径」每次扫描刷新，应用被移动位置后仍能被启动 |

### B. 覆盖层

| 编号 | 行为 |
|---|---|
| B1 | 按 ⌥+Space（可在控制台修改）唤起覆盖层，铺满**鼠标当前所在**屏幕，盖住所有窗口 |
| B2 | 再按一次该热键，或按 Esc，覆盖层收起 |
| B3 | 顶层显示所有分组文件夹方块（方块内为组内前 9 个应用的缩略图标）与未分组应用的单图标，平铺在同一网格 |
| B4 | 单击分组方块展开为该组应用的子网格；点击空白处或 Esc 返回顶层 |
| B5 | 单击应用图标启动该应用，并自动收起覆盖层 |
| B6 | 应用已在运行时，点击不新开实例，而是激活已有实例 |
| B7 | 别名生效：显示别名而非应用包内的名称 |
| B8 | 隐藏的应用不出现在覆盖层的任何位置，包括文件夹方块内的缩略图 |
| B9 | 方向键在图标间移动高亮，Enter 启动高亮项 |
| B10 | 直接输入字符时搜索框获得焦点并实时筛选；匹配范围是全部应用（跨分组），结果显示为平铺列表，不分组 |
| B11 | 搜索支持中文名、英文名、别名、拼音首字母（如 `wx` 匹配「微信」/「WeChat」） |
| B12 | 覆盖层内拖拽应用可改变组内顺序 |
| B13 | 在顶层把应用拖到分组方块上，该应用移入该组 |
| B14 | 在分组子网格里把应用拖到空白区域，该应用移回「未分类」 |
| B15 | 在顶层拖拽分组方块可调整分组顺序 |
| B16 | 分组或应用数量超出单屏网格容量时，网格可纵向滚动，不丢失任何条目 |

### C. 控制台 — 分组管理

| 编号 | 行为 |
|---|---|
| C1 | 点击 Dock 图标打开控制台窗口 |
| C2 | 新建分组、重命名分组、删除分组 |
| C3 | 删除分组时，组内应用全部移入「未分类」，不丢失应用 |
| C4 | 「未分类」不可删除、不可重命名 |
| C5 | 调整分组顺序 |
| C6 | 拖拽把应用移入/移出分组 |
| C7 | 空分组保留，不自动删除 |

### D. 控制台 — 单应用管理

| 编号 | 行为 |
|---|---|
| D1 | 设置别名；可清除别名恢复原名 |
| D2 | 隐藏应用；可恢复显示 |
| D3 | 锁定位置：锁定后该应用不被自动排序挤走 |
| D4 | 指定应用在所属分组内的排序权重 |
| D5 | 查看「失效」应用列表，可手动清理单条记录 |
| D6 | 查看应用详情：真实名称、bundleID、最近已知路径、所属分组、是否隐藏/失效 |

### E. 控制台 — 全局设置

| 编号 | 行为 |
|---|---|
| E1 | 修改唤起热键 |
| E2 | 调整网格列数、行数与图标尺寸 |
| E3 | 调整覆盖层背景模糊度 |
| E4 | 开关「是否包含 `/System/Applications` 的系统应用」 |
| E5 | 开关开机自启 |
| E6 | 退出 AppBox |

### F. 配置与方案

| 编号 | 行为 |
|---|---|
| F1 | 配置写入 `~/Library/Application Support/AppBox/` 下的 JSON 文件 |
| F2 | 导出当前配置为 JSON 文件到用户指定位置 |
| F3 | 从 JSON 文件导入配置 |
| F4 | 新建、切换、重命名、删除方案；一个方案一个 JSON 文件，同一时刻只有一个生效 |
| F5 | 一键重置当前方案 |

### G. 引导整理

| 编号 | 行为 |
|---|---|
| G1 | 首次启动（配置文件不存在）时打开控制台并进入引导整理向导 |
| G2 | 向导展示由 `LSApplicationCategoryType` 推导出的分组建议 |
| G3 | 每条建议可改名、与他组合并、删除、跳过 |
| G4 | 未声明类别的应用归入「未分类」 |
| G5 | 用户确认后才写入配置；若取消，配置为初始状态（仅「未分类」） |

### H. 性能

| 编号 | 行为 |
|---|---|
| H1 | 图标已缓存时，从按键到覆盖层可见的延迟低于 150ms |
| H2 | 首次全量扫描 100+ 应用耗时低于 1 秒 |
| H3 | 图标缓存到磁盘，二次启动不重新提取 |

## 6. 测试决策

### 接缝

唯一测试接缝是 `AppBoxCore` 导出的 `LibraryService`。它同时承担查询（返回渲染就绪的 `LibrarySnapshot`）与变更（分组、别名、隐藏、排序、方案）。

注入的端口（测试用假实现替换）：

| 端口 | 真实实现 | 测试实现 |
|---|---|---|
| `AppScanning` | FileManager 遍历标准目录 + 解析 Info.plist | 返回 fixture 数组 |
| `IconProviding` | NSWorkspace + 磁盘缓存 | 返回固定占位数据 |
| `Launching` | NSWorkspace.open | 记录被调用的 bundleID |
| `Watching` | FSEvents | 手动触发变更事件 |
| 文件读写 | 真实 `~/Library/Application Support/` | 内存文件系统 / 临时目录 |

### 自动化测试覆盖

- **扫描与合并**：fixture 含无 bundleID 的应用、重复 bundleID 的多个副本、嵌套 `.app`、非法 Info.plist → 断言最终的 `LibrarySnapshot`
- **配置往返**：编码 → 解码 → 再编码幂等；旧 schema 版本号能迁移到当前版本
- **分组操作**：新建 / 重命名 / 删除（断言组内应用落回「未分类」）/ 调整顺序 / 移动应用
- **「未分类」保护**：尝试删除或重命名「未分类」被拒绝
- **单应用操作**：设置与清除别名、隐藏与恢复、锁定后不参与自动排序、排序权重生效
- **失效判定**：配置有、扫描无 → 标记「失效」且不出现在快照的可见列表；手动清理后记录消失
- **搜索**：中文名、英文名、别名、拼音首字母、大小写不敏感；无结果时返回空列表
- **引导建议**：从 fixture 的 `LSApplicationCategoryType` 推导出建议分组；无类别的落入「未分类」
- **方案管理**：新建 / 切换 / 重命名 / 删除方案后，当前生效方案与磁盘文件一致

### 不做自动化测试的部分

覆盖层窗口（层级、焦点、多屏判定）、全局热键注册、真实图标提取、真实应用启动、FSEvents 触发、控制台 UI 交互。这些靠手工验证清单覆盖。

### 「完成」的定义

1. `swift build` 通过，无警告
2. `swift test` 全绿
3. `scripts/build-app.sh` 能产出可双击运行的 `AppBox.app`
4. 手工验证清单全部通过：
   - ⌥+Space 在任意应用前台时都能唤起覆盖层，且盖住全屏
   - 鼠标在副屏时唤起，覆盖层出现在副屏
   - Esc 与再次按热键都能收起
   - 单击应用能启动，已运行的应用被激活而非重复启动
   - 分组方块展开/返回正常
   - 搜索输入 `wx` 能匹配到中文名应用
   - 拖拽应用入组、拖出组、调整组顺序均生效且被持久化
   - 重启 AppBox 后所有配置保持不变
   - 新装一个应用后，下次唤起覆盖层能在「未分类」里看到它
   - 删掉一个已分组的应用后，控制台里出现「失效」条目，且覆盖层里不再显示
   - 导出配置 → 重置 → 导入，配置完全恢复

## 7. 明确不做

- 卸载应用、移动或删除磁盘上的应用文件（ADR-0004）
- 触控板捏合手势（ADR-0006）
- 自定义图标
- 覆盖层内右键菜单
- 标签制多归属分组（ADR-0002）
- Spotlight 全盘补扫（只扫标准目录）
- 多块屏幕同时覆盖（只盖鼠标所在那一块）
- 菜单栏图标
- 多选批量启动 / 一键启动组合
- 应用使用频率统计与「最近使用」排序
- 应用内更新、代码签名与公证、对外分发
- iOS / iPadOS 版本
- 云端同步配置

## 8. 补充说明

- 目标环境：macOS 26.7 (Tahoe)、arm64、Swift 6.4、仅有 CommandLineTools（无 Xcode）
- 实测本机 107 个应用，79% 声明了 `LSApplicationCategoryType`。类别分布不均：工具类 31、开发工具 17、效率 17。引导向导因此会给出偏粗的建议，且 Google Chrome 等 22 个未声明类别的应用会落入「未分类」——这是引导向导设计上必须接受的现实，不应试图用硬编码规则去猜。
- 权限：本方案不需要辅助功能权限，也不需要任何 TCC 授权（ADR-0006）。全局热键走 Carbon，应用扫描只读公开目录。
- 应用形态：常规应用（保留 Dock 图标），**不是** `LSUIElement` 代理程序。
- 图标缓存可能达到几十 MB，与配置文件物理分离，保证配置文件始终轻量、可随手备份。
- `Codable` 在字段变更时会直接解码失败，因此配置必须自带 schema 版本号与迁移入口（ADR-0005）。
