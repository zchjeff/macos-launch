# 控制台窗口骨架 + 分组管理

**Blocked by**: 006

**状态**：已完成（2026-09-26）——交互手势部分留了一份手工验证清单，见文末

## 目标

点击 Dock 图标打开控制台窗口，在其中新建/重命名/删除/排序分组，并把应用拖进拖出分组。这是「归纳整理」真正发生的地方。

## 涉及层

- [x] 数据层：无新增（复用 006 的分组模型；只给 `LibraryService` 补了一个 `reorder`）
- [x] 逻辑层：`ConsoleModel` 视图模型，全部变更经 `LibraryService`
- [x] UI层：控制台窗口（独立常规 `NSWindow`）、左侧分组列表 + 右侧应用列表、增删改排序交互、拖拽移入移出
- [x] 测试：分组操作的单元测试已在 006 覆盖；本切片补了 24 个「UI 动作 → `LibraryService` 调用」的映射测试

## 验收标准

- [x] 点击 Dock 图标打开控制台窗口（不是覆盖层）
- [x] 应用启动时（非首次）只静默常驻，不自动弹控制台（首启行为留给 015）
- [x] 控制台左侧列出所有分组（含「未分类」），右侧显示选中分组的应用
- [x] 能新建分组、重命名分组、删除分组
- [x] 「未分类」在界面上不可删除、不可重命名（菜单项直接禁用，不是点了才报错）
- [x] 删除分组前弹出确认，明确告知"组内 N 个应用将移入未分类"
- [x] 能拖拽调整分组顺序
- [x] 能把应用从右侧列表拖到左侧某个分组上完成移入
- [x] 能在右侧列表中调整应用顺序（顺序写入排序权重）
- [x] 所有变更立即持久化，重启 AppBox 后保持
- [x] 空分组在列表中保留，不自动消失

## 视图模型放在领域层

`ConsoleModel`（`Sources/AppBoxCore/ConsoleModel.swift`）不依赖 AppKit，只靠 `Observation` 的 `@Observable`：

```
"点了这个按钮会调什么、失败了会说什么" —— 这是本切片真正的新逻辑。
```

放在 AppBox 里就只能靠手点界面来验证；放在 AppBoxCore 里，24 个映射测试全都跑在假端口 + 临时目录上。视图那层因此退化成了纯接线，没什么可测的。

它是 `@MainActor` 的，`refresh()` 把阻塞的扫描（冷启动近半秒）丢到主线程外，回主线程再赋值——否则控制台一开就整窗卡住。

## 启动不再用 SwiftUI 的 `App` / `Scene`

`WindowGroup` 在启动时会自动开一个窗口，而验收标准要求「启动时只静默常驻」。所以 `main()` 直接拿 `NSApplication` 自己跑，窗口全部由 `AppDelegate` 管：

- 启动 → 注册热键、预热覆盖层，**不开任何窗口**
- Dock 图标（`applicationShouldHandleReopen`）→ 开控制台
- 关掉控制台 → 应用继续常驻，热键照常

顺带补了一份最小主菜单。这东西不是装饰：没有它就没有 ⌘Q，而且**文本框里的 ⌘C/⌘V 也不会响应**——AppKit 的编辑命令靠菜单项沿响应链派发，不是文本框自带的。

Dock 图标打开控制台时会先把覆盖层收起来，走的是新加的 `hideWithoutRestoringFocus()`：覆盖层在 `.screenSaver` 层级，不收起来会把刚打开的控制台整个盖住；而常规的 `hide()` 会先把焦点还给别的应用，紧接着控制台又抢回来，中间会闪一下。

## 删除要过确认，确认之前一个字节都不写

`requestDelete` 只在模型里记下待删的分组，`confirmDelete` 才调服务。`deleteConfirmationMessage` 说清楚「N 个应用将移入未分类」——「删分组」听起来像只删一个壳，用户得在点确认之前就知道有几个应用要挪窝。

顺带把 `GroupError` 与 `ConfigStoreError` 都接上了 `LocalizedError`：界面上的每一次拒绝都得有个说法。「点了没反应」和「操作被拒绝」在用户眼里是同一件事，而前者看起来就是坏掉了。

## 拖动：两条互不干扰的通道

侧栏的分组行同时要满足两件事——自己能被拖动排序（`.onMove`），以及能接住从右侧拖过来的应用（`.dropDestination`）。如果两种拖拽共用一种载荷（比如都用裸 `String`），就分不开了：拖分组的时候会被当成往组里放应用。

所以应用走一个专门的 `Transferable` 类型 `ApplicationDragPayload`（`com.ethicall.appbox.application`，在 `scripts/build-app.sh` 的 Info.plist 里声明）。同理，右侧的应用行**不能**用 `.onMove` 排序——`.draggable` 和 `.onMove` 在同一行上会打架，谁生效不好说。应用排序因此也走 `draggable` + `dropDestination`：落到行的上半区插到它前面，下半区插到它后面，与文件管理器一致。

行高会参与那个上下半区的判断，所以它写死成 `ConsoleView.rowHeight`。

## 排序权重从 1 开始编

`LibraryService.reorder(groupID:to:)` 按给定顺序把组内应用重编号成 1、2、3……

留出 0 是因为 0 是「还没有排序记录」的默认权重。手排过一个分组之后，新装的应用（权重仍是 0）会排在手排过的那些前面，而不是插进中间——`newApplicationSortsFirstAfterManualOrder` 把这个行为钉住了。

> **已推翻（011）**：011 把这条改成了「未编号的垫底」，测试也改名为 `newApplicationSortsLastAfterManualOrder`。原因见 011 的「未编号的排在最后」一节。

顺序由调用方给出，服务不自己按权重和名字重算：界面上的先后还取决于别名，而别名要等 011 才进配置，服务自己算出来的序会和用户看到的那一列对不上。

## 手工验证清单（需要人手）

自动化查不到的是**手势本身**，这几条得真点一遍：

1. 点 Dock 图标 → 控制台弹出；再点一次 → 已经在前台，不重复开窗
2. 侧栏右键分组 → 重命名、删除两项；「未分类」这两项应当是灰的
3. 删除一个非空分组 → 确认框里应写着「N 个应用将移入「未分类」」；取消后什么都不变
4. 拖动侧栏的分组行 → 能上下换位（确认没被「拖应用进来」的落点吃掉）
5. 从右侧把一个应用拖到侧栏某个分组行上 → 计数 +1，应用从当前列表消失
6. 在右侧列表里拖动应用 → 上下换位；拖到行的下半区应落到目标后面
7. 关掉控制台后按 ⌥+Space → 覆盖层照常唤起

## 备注

- 控制台是配置的**唯一写入场所**（覆盖层内拖拽除外，见 012）
- 控制台不做卸载、不做自定义图标（ADR-0004、spec 明确不做）
- 别名与隐藏还是 `snapshot(aliases:hidden:)` 的调用方入参，控制台这一层暂时看不到它们，等 011
- **后续变更（011）**：本文里「未编号的权重 0 排在手排过的前面」已被推翻——011 改成垫底，原因见 `011-单应用管理与失效列表.md` 的「未编号的排在最后」一节。别名与隐藏也在 011 进了配置，不再是调用方入参。
