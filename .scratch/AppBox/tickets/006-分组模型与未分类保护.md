# 分组模型与「未分类」保护

**Blocked by**: 005

**状态**：已完成（2026-09-26）

## 目标

应用能被归属到分组，且"应用永不丢失"这条不变量成立：删掉一个分组，组内应用全部落回「未分类」，不会有应用凭空消失。

## 涉及层

- [x] 数据层：`Group` 模型（id、名称、顺序）；配置中记录每个应用的归属分组
- [x] 逻辑层：归属制语义（一个应用属于唯一分组）；新建/重命名/删除/排序分组；移动应用；「未分类」保护
- [x] UI层：无（领域层切片，靠单元测试验证）
- [x] 测试：分组增删改、移动、未分类保护、快照组装

## 验收标准

- [x] 一个应用在任一时刻只属于一个分组
- [x] 「未分类」是系统保留分组：**不可删除、不可重命名**
- [x] 尝试删除或重命名「未分类」时操作被拒绝（返回明确错误，不静默失败）
- [x] 删除一个分组时，组内所有应用移入「未分类」，一个都不丢
- [x] 删除分组不影响应用的其他配置
- [x] 调整分组顺序后持久化，重启保持
- [x] 空分组保留，不自动删除
- [x] 快照按分组组装：每个分组含其应用列表（已按排序权重排好），外加未分类应用
- [x] 单元测试覆盖以上每一条

## schema v2

`AppBoxConfig` 抬到 2：新增 `groups` 与 `applications`。`applications` 是 `bundleID → ApplicationConfig`，只记「有配置的应用」，没出现的按默认值（未分类、权重 0）处理——这样配置文件里不会躺着 108 条全是默认值的记录。

迁移步骤 1→2 只改版本号：新增字段在 `init(from:)` 里用 `decodeIfPresent` 给了默认值，所以老文件解出来自然是「一个未分类组 + 零条应用配置」，不需要在迁移里补字段。

**新增字段的默认值写在解码器里，不是写在迁移步骤里。** 这样 2→3 加字段时同样不必抬版本号，迁移表不会随着字段数增长而膨胀。

## 分组顺序用数组位置表示

没有 `Group.order` 字段。配置里 `groups` 的数组顺序就是展示顺序。

存一个 `order` 字段意味着两个真相来源：数组顺序和 `order` 值，两者不一致时谁说了算？JSON 里 `groups` 本来就是有序数组，`Codable` 原样保序，重新排序就是移动数组元素。多存一个字段只会多一种坏掉的方式。

## `normalized()`：不变量只在一处修复

配置是可以手改的（ADR-0005），所以「未分类一定存在」和「应用不指向不存在的分组」这两条不变量在读取时会被破坏。修复动作集中在 `AppBoxConfig.normalized()`：

- 少了「未分类」→ 补到首位
- 应用的 `groupID` 指向已消失的分组 → 改写为「未分类」

`load()` 解码后调它，`mutate()` 落盘前也调它。**一次写入不论从哪条路径进来，落盘的形态都合法。**

这条是「应用永不丢失」的最后一道防线：即使配置文件被手工删掉某个分组，指向它的应用也只会掉进「未分类」，不会因为找不到归属而消失。

## `LibraryService` 从无状态结构体变成加锁的类

原本（004）是 `struct`，每次 `snapshot()` 现扫现拼、无状态。006 要读写配置，就得持有状态，于是改成 `final class` + `NSLock`，标 `@unchecked Sendable`。

- 读路径 `snapshot()` 与 `currentConfig` 只取锁里的快照，不影响覆盖层唤起性能。
- 写路径统一走私有 `mutate(_:)`：**先在草稿上改，`normalized()` 之后先 `save()` 落盘，写成功了才把内存里的 `config` 换掉。** 落盘失败时内存保持原样，不会出现「界面上显示改了、磁盘上没改」这种两处各说各话的状态。

`schemaVersion: 99` 那种高版本文件被拒时 `usableConfig` 是 `nil`，`init` 落到 `AppBoxConfig()` 默认值——这是明确的降级，因为拒绝加载已经意味着「没有可信配置可用」。

## 快照按分组组装

`LibrarySnapshot` 从「一维应用列表」改成 `groups: [GroupSnapshot]`，并留了一个 `allApplications` 投影（跨分组平铺）。

两处用到这个投影：009 搜索要的是平铺形态；007（覆盖层文件夹方块）落地之前，004 的覆盖层也是拿它渲染的——所以这次改动没有让覆盖层倒退，`OverlayView` 只换了取数据的入口。

排序权重：`orderWeight` 小的在前，同权重按显示名，最后用 `bundleID` 兜底。**兜底项是必须的**——否则权重和显示名都相同时比较不构成全序，`sorted` 的结果会随扫描顺序漂移（003 踩过同一个坑）。

## 测试

`Tests/AppBoxCoreTests/GroupTests.swift`，4 个 suite 共 19 个用例。全部套件 92 个测试通过。

`ServiceFixture` 里有一个刻意的设计：`service` 是计算属性，**每次访问都新建一个服务并从磁盘重读配置**。所以它天然模拟「重启」——上一次改动如果没真正落盘，下一次访问就看不见。`mutationsSurviveRestart`、`deletionIsPersisted`、`reorderingSurvivesRestart` 三个用例靠的就是这个。

## 一处未完全覆盖的验收标准

「删除分组不影响应用的**别名、隐藏**、排序权重等其他配置」——别名与隐藏目前还不是配置字段，它们是 `snapshot(aliases:hidden:)` 的调用方入参（005 留下的形态，等 011/013 落到配置里）。所以这条现在只能用 `orderWeight` 验证。

结构上不会出问题：`deleteGroup` 只重写受影响应用的 `groupID`，其余字段一概不碰（`deletionKeepsOtherApplicationSettings` 覆盖了权重这一项）。等别名与隐藏进配置后，这条标准需要补一个真正的用例。

## 备注

- 采用归属制而非标签制，理由见 ADR-0002。若日后要表达"同一应用出现在多组"，应引入独立的置顶收藏区，而不是改成标签制
