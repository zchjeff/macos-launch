# 单应用管理 + 失效列表

**Blocked by**: 010

**状态**：已完成（2026-09-26）——交互手势部分留了一份手工验证清单，见文末

## 目标

在控制台里对单个应用做展示层调整：改别名、隐藏、锁定位置、指定排序权重；并能看到「失效」应用列表并手动清理。

## 涉及层

- [x] 数据层：配置中每个应用的 `alias` / `hidden` / `locked` / `lastKnownPath` 四个新字段；`schemaVersion` 仍是 2
- [x] 逻辑层：别名、隐藏、锁定、权重排序、失效判定与清理，全部落在 `LibraryService`
- [x] UI层：应用详情面板（inspector）、列表徽标与置灰、失效列表视图、别名输入 sheet、清理确认框
- [x] 测试：+41 个（117 → 158，18 → 26 个 suite）

## 验收标准

- [x] 设置别名后，覆盖层显示别名 —— 分组方块缩略图那半边留给 007（见「备注」）
- [x] 别名可清除，清除后恢复真实名称
- [x] 隐藏应用后，它从覆盖层消失，但控制台里仍可见并可恢复 —— 方块缩略图那半边留给 007
- [x] 隐藏不影响应用在系统中正常运行
- [x] 锁定位置后，该应用在所属分组内不被自动排序挤走
- [x] 排序权重生效：分组内应用按权重排序，未指定权重的排在最后、再按显示名排
- [x] 应用详情显示：真实名称、bundleID、最近已知路径、所属分组、是否隐藏、是否锁定、是否失效
- [x] 「失效」列表显示所有「配置有、磁盘上找不到」的应用
- [x] 可从失效列表中清理单条记录；清理后该应用的别名/分组/隐藏配置一并移除
- [x] 失效应用不出现在覆盖层的任何位置
- [x] 单元测试：设置/清除别名、隐藏/恢复、锁定、权重排序、失效判定与清理

## 新增字段不抬 schema 版本号

`alias` / `hidden` / `locked` / `lastKnownPath` 全走手写 `init(from:)` 里的 `decodeIfPresent` 给默认值。按 006 立下的规矩，**抬版本号只留给「老文件会被解错」的改动**：判断标准是新增可选字段加上默认值之后，旧文件解出来的语义是否还和当初写进去的一致——别名默认没有、隐藏默认否、锁定默认否，都是「本来就没说过」的意思。`decodesApplicationWithoutNewerFields` 拿一份只有 `groupID` + `orderWeight` 的 v2 JSON 钉住了这条。

顺带把 `normalized()` 扩成一次修两组不变量：分组 ID 指向不存在的组就落回「未分类」（006 的行为），别名 trim 后为空就当作没设——手改配置的人很可能只删了引号里的字、留下一个空串。

## 「失效」是算出来的，不是存出来的

配置里有、这次扫描里没有，就是失效（`MissingApplication`）。没有 `isMissing` 这种落盘字段：磁盘是唯一的真相来源，标记一旦落盘就会和实际状态漂移，还要处理「标记失效了但应用又装回来了」。

能算的前提是配置里留着一条线索。`lastKnownPath` 就是它——`snapshot(recordingPaths: true)` 顺手把扫到的位置记进**已经在配置里有条目的**应用。只记已跟踪的那部分是有意的：108 个应用全记一遍意味着配置文件里凭空多出 100 多条记录，而用户真正关心的只是自己动过的那几个。控制台开窗时调这一路；覆盖层不调，覆盖层的唤起路径上一个字节都不该写盘（017 的硬指标）。

失效列表因此只对「动过设置的应用」有效，没动过的应用从磁盘上消失就是彻底消失——这不影响可清理性，因为它本来就没有设置可清理。

## 锁定的语义：位置冻结

`locked` 锁的是**位置**，不是「不许操作」：改名、隐藏、移出分组照旧，只有排序不再能挤动它。

实现上，锁定瞬间把整组的编号写实（1、2、3……），此后 `reorder` 走的是「保留槽位」的算法——先把锁定成员占的槽位留出来，剩下的槽位按调用方给的顺序填。这样解锁之后它仍待在原先的位置，不会因为期间别人排过队而漂走。

拖动路径上有两道闸：`move(toGroup:)` 对锁定应用直接抛 `GroupError.applicationLocked`；控制台也不给锁定的行挂 `.draggable`。前者是兜底，后者才是用户看得见的反馈——不能拖的行不该长得像能拖的。

## 未编号的排在最后（推翻了 010 的决定）

010 当时定的是「权重 0 = 还没排序，排在手排过的前面」，理由是「新装的立刻看得见」。011 把这条翻了过来：**没编号的垫底**。

翻的原因就是锁定本身：一旦位置能锁，「没编号」和「排在第 1 位」必须能区分开——否则锁在队首的应用和被锁到「未编号」的应用在配置里长得一样，`lockedApplicationKeepsItsSlot` 这类断言就没法写。而「新应用要看得见」这个诉求，真正该在 015 的首启引导里解决，不该靠一个会让手动排好的队被反复打断的排序规则。

同权重的冲突规则也在这里定死：显示名 `localizedStandardCompare`（别名参与，因为用户排的是他看见的那一列），再拿 bundleID 兜底成全序。没有兜底的话，两个同名应用在两次扫描间的相对顺序会随机抖动。都写在 `Ordering.precedes` 的注释里。

## 编号要就地补条目

`reorder` 与 `setLocked` 都走 `number(_:in:of:)` 给一组应用重新编号。这个函数是拆出来的，因为最初那版写了 `config.applications[member]?.orderWeight = position + 1`——可选链上的赋值在条目不存在时**静默什么都不做**，于是从没动过设置的应用编不上号（权重仍是 0，垫底），锁定的位置也就锁了个寂寞。测试里表现为「锁定后还是被挤走了」，查了半天才落到这行。现在它会顺手补一条 `ApplicationConfig()`。

## 没变化就不写盘

`mutate` 里加了 `guard normalized != config else { return }`。读路径上也有会走 `mutate` 的东西（记录 lastKnownPath），不加这道闸的话，开一次控制台就会把配置文件重写一遍——文件的时间戳天天在变，用户也不敢手改（ADR-0005 允许手改）。

## 视图层拿到的是投影，不是配置

`LibrarySnapshot` 里原本有个 `allApplications`，现在删了，只剩 `visibleApplications`。「隐藏的应用不出现在覆盖层」这条规则因此**只有一个地方能被违反**（`GroupSnapshot.visibleApplications` 那个 filter），而不是「谁想起来谁就自己 filter 一下」。覆盖层直接遍历它。

`hidden` 这个字段的全部读取点：那个 filter，加上控制台自己的徽标与置灰。启动路径从头到尾不读它——所以「隐藏不影响应用正常运行」不是靠小心，是靠没有代码路径能影响。

详情面板的数据是 `ApplicationDetail`，它有两种来源：在场的应用（`ApplicationEntry`）和失效的记录（`MissingApplication`）。两种都映射成同一个类型，面板因此只有一套渲染逻辑；`isMissing` 一开，状态开关就退回成只读的值展示（`ApplicationInspector.toggle(_:set:)` 返回 nil 的 Binding）——磁盘上已经没有这个应用了，隐藏/锁定它没有任何意义。

## 控制台的选中状态不是字符串

侧栏的选中项从「分组 ID 字符串 + 空串表示未分类」换成了 `ConsoleSelection` 枚举（`.group(String)` / `.missing`）。哨兵字符串那种写法，等失效列表这第三个入口一进来就会散架：`""` 到底是未分类还是没选？枚举让「没有分组叫这名」和「未分类」在类型上就分得开。

顺带修了一个真 bug：「换分组后原先选中的应用不再占着详情面板」这条第一次是红的。`createGroup` 先 `perform`（内部已 refresh + apply）再设 `selection`，于是「选中项变了要重新校验详情」那段逻辑根本没机会跑。改成 `selection` 是计算属性、setter 里顺手校验，无论谁先谁后都对。

## 验证

**代码侧**：158 个测试通过（26 个 suite）。本切片新增 41 个，覆盖别名（含 `[nil, "", "   "]` 三种清除写法）、隐藏、锁定与解锁、权重排序与同权重冲突、失效判定与清理、详情投影、确认框文案。

**真机侧**（截图权限时有时无、辅助功能权限被拒，所以下面这些是能查的部分）：

- 控制台：侧栏出现「维护 / 失效应用 2」；分组行显示「N 个应用（M 个已隐藏）」
- 详情面板：选中被锁定的 Maps → 真实名称 / bundleID / 路径 / 所属分组 齐全，两个开关一开一关，别名「未设置」+「设置…」；同组被隐藏的「国际象棋」行置灰、带眼睛斜杠徽标
- 失效列表：两条记录（`com.apple.Music2` 与一条别名「早就没了」的），副标题是「bundleID — 最后待过的位置」，点「清理…」弹确认框；选中一条 → 详情显示「已失效」、真实名称「—」、最后待过的位置、三个开关全是灰的只读值
- 覆盖层①（隐藏）：手写一份「108 个里隐藏 103 个」的配置，重启后覆盖层只剩 5 个图标，与控制台的分组计数一致
- 覆盖层②（别名）：给 Music 设别名「听歌的」、Terminal 设「命令行」，再将两者之外的全部隐藏 → 覆盖层里这两个图标下方显示的正是别名；同一次还带上了 `com.apple.Chess` 的别名「棋」，它因为是隐藏的而完全不出现

第一次跑覆盖层验证时看到 40 个图标，一度以为隐藏没生效——实际是**验证脚本自己**解析 `--scan` 输出时按列取 ID，碰到显示名带空格的应用（`Activity Monitor`）就错位，这些应用压根没进配置、于是按默认「可见」渲染。顺带撞出一个真实边界：`/Applications/AnyConnect.app` 没有 `Info.plist`，扫描器按 003 的既有约定拿**路径当 bundleID**（`AppScanner.swift:67-69`），配置里存的也是这个路径——这是设计好的兜底，不是 bug，但验证脚本得认它。

## 手工验证清单（需要人手）

自动化查不到的是**手势本身**，这几条得真点一遍：

1. 点 Dock 图标 → 控制台弹出；点左侧某个分组，再点右侧某个应用 → 右侧详情面板出现
2. 详情里打开「在覆盖层隐藏」→ 该行变暗、出现眼睛斜杠徽标、分组计数出现「M 个已隐藏」；按 ⌥+Space 唤出覆盖层，它不见了；关掉开关后覆盖层里回来
3. 详情里「设置…」→ 输入别名 → 保存：左侧列表、右侧详情标题、覆盖层三处都换成别名；点「清除」恢复真实名称
4. 打开「锁定组内位置」→ 该行出现锁徽标、拖不动（别的行照旧能拖）；把同组别的应用拖到它前面 → 它不动；解锁后能排
5. 把锁定的应用拖到侧栏另一个分组上 → 会被拒绝，界面上有说法（不是没反应）
6. 侧栏「维护 / 失效应用 N」→ 右侧列出失效记录；右键一行 →「清理这条记录」；点「清理…」→ 确认框里写明「别名、分组、隐藏等设置都会被清掉」；确认后少一条，取消后一个字节都不变
7. 别名输入框里敲纯空格 → 保存后应当等同于「没设别名」，而不是显示一片空白
