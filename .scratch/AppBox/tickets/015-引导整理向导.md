# 引导整理向导

**Blocked by**: 014, 010

**状态**：已完成（2026-09-26）

## 目标

首次启动时打开控制台并进入引导整理向导，展示由系统类别推导出的分组建议，用户逐个确认/改名/合并/删除后才写入配置。

## 涉及层

- [x] 数据层：无新增字段（写入既有的分组配置），但 `applySetup` 是配置的第一个「整批写入」入口
- [x] 逻辑层：`CategoryCatalog`（类别 → 分组的唯一出处）、`SetupAdvisor`（推导建议）、`SetupWizardModel`（逐条编辑 + 一次落盘）
- [x] UI层：`SetupWizardView`（720×580 sheet，建议列表 + 长度条 + 行内菜单 + 取消/确认）、`SetupRenameSheet`
- [x] 测试：`SetupAdvisorTests`（12）+ `SetupWizardTests`（24），166 → 202 个测试、27 → 31 个 suite

## 验收标准

- [x] 首次启动（配置文件不存在）时打开控制台并进入引导整理向导
- [x] 向导展示由 `LSApplicationCategoryType` 推导出的分组建议，每条建议显示分组名与包含的应用
- [x] 类别到分组名的映射是**数据驱动**的（一张表），不是散落在代码里的 `if/else`
- [x] 未声明类别的应用全部归入「未分类」
- [x] 每条建议可：改名、与他组建议合并、删除（该组应用回到「未分类」）、跳过
- [x] 用户确认后才写入配置
- [x] 若用户取消向导，配置为初始状态（仅「未分类」，所有应用都在其中）
- [x] 向导只出现一次；之后启动不再弹出
- [x] 本机实测：108 个应用、86 个有认得出的类别 → 16 条建议、86 个应用归位、22 个留在「未分类」；大组「工具 32 / 开发工具 18 / 效率 16」（预估 31/17/17）。长度条按最大组取比例，谁大谁小一眼看得出来
- [x] 单元测试：fixture 覆盖"全部无类别"、"只有一个类别"、"类别分散在 17 个"、"某类别只有 1 个应用"

## 表是唯一的分类知识出处

`CategoryCatalog` 就是一张 `[String: String]`：加一个类别只加一行，任何地方都不允许再长出「如果是工具类就……」的分支——那种写法每加一个类别都要改代码，第一个特例出现之后就会有第二个。

标准表列的是 App Store 的常用类别。表里没有的值**不是错误**：调用方把它们连同原始值一起留在「未分类」，界面上说一句「有 N 个类别本程序还不认识（值…）」。这条既有明确归属，也给维护的人留了线索——照着提示往表里补一行即可。

补 `board-games` 这一行就是这么来的：真机首启时提示里冒出 `public.app-category.board-games`，查出是 Chess.app 声明的（Games.app 声明的是 `games`），两者显然都该叫「游戏」。加上这一行之后，Chess 靠「同名合并」进了「游戏」，未分类从 23 个降到 22 个——与预估数字对上。

## 「跳过」的语义是补出来的

规格（G3）没定义跳过。实现时定成：**这次先不采纳**，不是「这条建议错了」——建议留在列表里，标着「已跳过」，随时可以恢复。对配置的效果与删除完全一样（不建这个组，应用留在「未分类」），差别只在可恢复性，以及界面上还看得见它。

不选「跳过 = 删除」是因为向导本身可取消：如果跳过和删除的界面表现都一样，用户就没法在最后一屏回看自己放弃了什么。

## 一次算好、一次落盘

模型里 `confirm()` 把当前采纳的建议编成 `[GroupPlan]`，交给 `LibraryService.applySetup` 一次性写完：建组、改归属全在同一个 `mutate` 里，不合法就整体拒绝（组名先统一验一遍，再动手写）。

`mutate` 这次多了 `forcingWrite`。**「配置文件是否存在」就是「首启是否已经过去」的标志**——所以向导结束时即使配置内容没变（用户把建议全删了、或者直接取消），也必须把文件落实下来，否则下次启动向导又冒出来。取消因此走的是「采纳一个空计划」，配置落成初始状态：只有「未分类」，应用全在其中。

`mutate` 的写入判据仍是「归一化之后有没有变化」；`forcingWrite` 只把这一条让开，没有第二条写盘路径。

## 逐条编辑都是内存操作

改名、并入、删除、跳过都只动 `suggestions` 数组，一个字节不落盘（模型类注释里写着这句，测试也钉着）。所以向导里的每次点击都随时可以「取消」重来，删除一条建议不必弹确认框——为一次可逆的内存操作弹窗，比不弹更烦人。

两处校验值得一说：

- 改名去空白；空名和与别的建议重名都拒绝，**不自动合并**——用户想合成一组时该用「并入」，自动合并只会让他看到一条凭空少了的建议。
- 「未分类还剩多少」= 总数 − 各条建议人数之和。直接相减是成立的：一条建议对应一个类别，一个应用只有一个类别，所以各条建议名下的应用互不重叠。这条推理在属性上有注释，免得以后有人以为这是巧合。

## 验证

**代码侧**：202 个测试通过（31 个 suite）。本切片新增 36 个：推导（排序、同名合并、无类别、单一类别、类别分散、未识别值、空扫描）+ 模型（改名/空名/重名、并入的成员与顺序、删除、跳过与恢复、计数、确认写出的分组与归属、只改归属时保留别名/隐藏/锁定、组名不合法整体拒绝、空计划也写盘、取消后配置为初始状态、从控制台进出向导）。

**真机侧**（把用户的 `default.json` 备份后移走，制造首启；验完全部还原，sha 一致）：

- 首启：控制台 + 向导 sheet 打开，数字「采纳 16 条建议，86 个应用归位；22 个留在「未分类」」，与 plist 里的类别统计（108 个应用、86 个有类别）逐个对得上。
- 未识别提示（补 `board-games` 之前的构建上观察到）：「有 1 个类别本程序还不认识（public.app-category.board-games），这些应用先留在「未分类」。」
- 行内菜单（计算机控制点击）：「重命名…／并入…（子菜单列出其余 15 组）／跳过这一条／删除这一条」。点「跳过这一条」后该行变「已跳过」、摘要变「采纳 15 条建议，54 个应用归位；54 个留在「未分类」」；改名 sheet 把「工具」改成「系统工具」后行名当场变、计数不变。
- 确认：点「确认整理」→ `default.json` 落盘，`schemaVersion 2`、17 个分组（未分类 + 16）、86 条归属记录（22 个没动过的应用不产生记录）；控制台侧栏随后就显示了这 16 组。
- 取消：点「取消」→ 配置 137 字节、只有「未分类」、零条应用记录；控制台显示「未分类 108 个应用」。
- 只出现一次：确认之后、取消之后各重启一次，应用在跑但零窗口（没有向导），且配置文件未被改写（inode/mtime/大小都不变）。
- 反证：控制器只挂了这一次向导；验证完毕后用户原配置已按 sha 还原、临时文件清理、进程退出。

**一处未受控写盘的观察**：验证中途出现过一次没有由我发起的写盘（结构与上一次确认写出的相同、UUID 不同）。随后两次干净首启——连续轮询 25 秒以上、加上状态读取与截图——都复现不出「自己写」；代码里也只有 `confirm`/`cancel` 两条写路径（按钮动作）。判断是当时有一次外部点击落在了刚弹出的向导上（辅助功能助手重放或人手），不是应用自身的路径，记录在此备查。

## 手工验证清单（需要人手）

自动化点不到的是「用起来顺不顺手」，这几条得人来做一遍：

1. 第一次启动（删掉 `~/Library/Application Support/AppBox/default.json` 后重开）：向导应在控制台里弹出来，列表能滚、长度条能看出「工具」最长
2. 给一条长建议改名、把两条并起来、删掉一条：每一步都该当场生效，确认后控制台的分组与刚才屏幕上的样子一致
3. 把建议全删光：确认后所有应用都在「未分类」，空状态提示应说清这一点
4. 向导里按「取消」：控制台不应出现任何新分组
5. 再启动一次：向导不该再出现（这是「只出现一次」的最终判据）

## 备注

- 本切片只做「首启整理」；新装应用落进「未分类」是 014 的产物，之后的分组维护靠控制台（010/011）
- 窗口固定 720×580；建议条目本身没有上限，「工具」这类大组在列表里是可滚动的，不折叠——折叠会让人看不见它有多大
- 分类只到「工具」这一层，一个类别动辄几十个应用。设计上不试图猜得更准：推出来的东西只管给用户一个能改的起点，改得动、删得掉、能合并，比猜得准重要
