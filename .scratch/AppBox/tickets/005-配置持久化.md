# 配置持久化：JSON + schema 版本 + 方案文件布局

**Blocked by**: 003

**状态**：已完成（2026-09-26）

## 目标

配置能落盘并在重启后恢复。文件落在 `~/Library/Application Support/AppBox/`，带 schema 版本号与迁移入口，为后续所有切片提供持久化基座。

## 涉及层

- [x] 数据层：`AppBoxConfig` 可编码模型（含 `schemaVersion`）；方案文件布局（一方案一 JSON）
- [x] 逻辑层：读写、原子写入、schema 版本校验与迁移入口、损坏配置的降级处理
- [x] UI层：无（通过单元测试与调试命令验证）
- [x] 测试：编解码往返幂等、版本迁移、损坏文件降级、原子写入

## 验收标准

- [x] 配置写入 `~/Library/Application Support/AppBox/` 下的 JSON 文件
- [x] 编码 → 解码 → 再编码结果幂等
- [x] 配置含 `schemaVersion` 字段；遇到低版本配置能迁移到当前版本
- [x] 遇到**高版本**配置（比当前代码新）时拒绝加载并给出明确提示，不静默丢数据
- [x] 遇到损坏的 JSON 时降级为默认配置，且把损坏文件改名备份，不直接覆盖
- [x] 写入是原子的（写临时文件再 rename），进程中途被杀不会留下半截文件
- [x] 图标缓存位于同目录子文件夹 `icons/`，与配置文件物理分离
- [x] 单元测试使用临时目录，不触碰真实的 `~/Library/Application Support/`

## 文件布局

```
~/Library/Application Support/AppBox/
├── default.json      ← 一个方案一个文件，直接躺在这里
├── 工作.json
└── icons/            ← 图标缓存，与配置平级
```

配置**没有**放进 `profiles/` 子目录。ADR-0005 写的是「图标缓存放在同目录的子文件夹」，验收标准写的是「配置写入 `.../AppBox/` 下的 JSON 文件」，两处都指向「配置在 AppBox 目录下、`icons/` 是其唯一子目录」。

## 在真实目录上验证时抓到的一个数据丢失 bug

`--config` 第一次跑通之后，我在真实目录上手工喂了一份 `schemaVersion: 99` 的文件，结果是：

```
加载结果：拒绝加载——文件版本 99，本程序支持 1
          文件未被修改，请升级 AppBox 或手工处理该文件
```

**两行之后，那个文件被覆盖成了 `schemaVersion: 1`，`futureField` 没了。**

`load()` 的拒绝是对的，问题出在 `save()`：它不知道自己要写的那份文件版本更高，照写不误。当时 `ConfigCommand` 在加载之后无条件做了一次「写一遍再读回来」的往返验证，正好踩中。

这条路径在真实使用里完全走得通：用户在新版 AppBox 里配好了一切 → 降级回旧版 → 旧版拒绝加载但照常启动 → 用户随手改一个设置 → 新版的字段全部消失。

修法是两处：

- `save()` 写之前先看一眼磁盘上那份的 `schemaVersion`，比当前新就抛 `wouldOverwriteNewerSchema`。只守住 `load()` 是不够的，拒绝一次读取挡不住后面任何一次写入。
- `ConfigCommand` 只在 `createdDefault` 分支写文件。刚打印完「拒绝加载」就转头覆盖，是命令自己的逻辑和自己打印的结论打架。

回归测试：`保存时发现磁盘上那份版本更高就拒绝写入，不抹掉不认识的字段`。

## 实施中偏离原计划的地方

- **`ConfigStoreError` 多了 `wouldOverwriteNewerSchema` 一档**，原计划只有 `invalidProfileName` 与 `unsupportedSchema`。理由见上。它不是防御性编程——是真实目录上跑出来的。
- **迁移入口是一个 `guard` 而不是一个循环。** 最初写成 `while version < current` + `switch` 的逐级升级框架，编译器报 `variable 'version' was never mutated`——因为当前一档迁移都没有，那段循环是死代码。改成 `migrated(_:from:)`：版本不等于当前就拒绝，函数体留成扩展点，注释里写明第一次改字段时怎么把它变成循环。**版本号认不出来一律拒绝，不当成损坏去覆盖**——文件内容没坏，只是本程序不认识。
- **`load()` 用返回值表达四种结果，而不是「抛错 + 返回值」混用**。高版本那一档 `refusedUnsupportedSchema` 不携带配置，调用方拿不到可以顶上去的默认值，就没法静默继续跑。
- **方案名做了校验**（挡掉空、`/`、`\`、前导 `.`）。方案名会变成路径的一段，控制台之后会让用户输入它，这是文件写入的边界。

## 验证方式

- 单元测试 16 个用例（含参数化的非法方案名），全部用临时目录，覆盖：往返幂等（字节相同）、高/低版本拒绝且原文件不动、损坏降级与备份内容保留、两次损坏不互相覆盖、目录自动创建、写入后无临时文件残留、一方案一文件。
- 真实目录上跑 `--config`，四种结果各走一遍：首次创建 → 再跑读到配置 → 损坏降级（备份文件 `default.corrupt-2026-09-26-224612.json` 内容完好）→ 高版本拒绝（`md5` 前后一致）。
- `AppBoxIdentityTests` 补一条：配置文件与 `icons/` 平级，不被塞进子目录。
