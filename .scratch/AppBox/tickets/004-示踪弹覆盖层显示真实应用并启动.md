# 【示踪弹】覆盖层显示真实应用 + 单击启动收起

**Blocked by**: 002, 003

**状态**：已完成（2026-09-26）

## 目标

按 ⌥+Space 唤起覆盖层，看到的是**磁盘上真实的应用**，单击任一图标能启动它并自动收起覆盖层。这是第一条端到端打通的路径，证明整个架构成立。

## 涉及层

- [x] 数据层：`LibraryService` 门面 + `LibrarySnapshot`（渲染就绪的扁平应用列表）；注入端口 `AppScanning` / `IconProviding` / `Launching`
- [x] 逻辑层：扫描结果与配置合并为快照；隐藏的应用不进快照
- [x] UI层：覆盖层网格渲染真实图标与显示名；单击启动；启动后收起
- [x] 测试：`LibraryService` 快照组装的单元测试，用假端口注入

## 验收标准

- [x] 覆盖层网格显示真实应用的图标与名称，排版与数量正确
- [x] 图标来自 003 的磁盘缓存，唤起时无可见的加载卡顿
- [x] 单击图标能启动对应应用
- [x] 启动后覆盖层自动收起
- [x] 应用已在运行时，单击**激活已有实例**，不新开一个实例
- [x] 别名未设置时显示应用真实名称
- [x] 单元测试：假扫描器喂 fixture，断言 `LibrarySnapshot` 的应用列表、主键、排序
- [x] 单元测试：`Launching` 假实现能断言"被调用的 bundleID 与点击的一致"
- [x] 从按键到覆盖层可见的延迟 < 150ms（spec H1，图标已缓存的前提下）

## 实测数据（本机 arm64，108 个应用）

| 场景 | show() | 首次绘制 | 合计 |
|---|---|---|---|
| 冷唤起（图标已缓存、进程内第一次） | 17.4 ms | 5.7 ms | **23.0 ms** |
| 温唤起 | 6.2 ms | 1.9 ms | **8.1 ms** |
| 连续 20 次中位数 | — | — | **8.6 ms**（最小 3.6 / 最大 9.7） |

中途走过的弯路与最终做法的差距：最初每次唤起都重建全屏窗口 + 同步重扫描，实测 227 ms，**超标 1.5 倍**。两处改动把它压到 8.6 ms：

1. **窗口只建一次**，收起时 `orderOut` 而不销毁。重建一个全屏窗口连同它的 SwiftUI 视图树要 60 ms 以上。
2. **快照移出唤起路径**（见下）。重扫描要读 108 个 Info.plist，约 30 ms。

## 实施中偏离原计划的地方

- **`LibraryService.snapshot()` 不在 `show()` 里同步调用，改为后台刷新。** 触发点：ticket 017 写死了「覆盖层唤起路径上**不做**同步的文件 IO：图标必须在启动时预加载或异步加载，唤起时只读内存」。原实现每按一次热键就扫一次盘，直接违反这一条。现在 `show()` 只碰内存，`refresh()` 用 `Task.detached` 在后台重算，回主线程后**仅在快照真的变了时**才给 `rootView` 赋值。
- **`OverlayController` 增加 `prewarm()`**，由 `AppDelegate` 在启动时调用一次，避免第一次按键落在冷路径上。启动时那次全量扫描（缓存冷时 496 ms）发生在后台，不阻塞覆盖层。
- **单击语义抽成 `OverlayController.activate(_:)`**，而不是留在视图闭包里。一是给这个行为一个名字，二是让「启动 + 收起」两件事能被一次调用验证。
- **`OverlayView` 增加进程内图标缓存 `IconImageStore`（`NSCache`）。** 磁盘缓存解决的是"不重复向系统要图标"，但 SwiftUI 每次求值 `body` 都会重新构造 `NSImage`；覆盖层每次唤起都重建视图树，没有这层就会反复读同一批 PNG。

## 验证方式

- **渲染正确性**：应用自渲染覆盖层视图到 PNG（`bitmapImageRepForCachingDisplay`），肉眼核对 7 列网格、真实图标、显示名与截断。截图确认 108 个应用、无缺图标的条目。
- **启动与激活**：临时探针驱动 `OverlayController.show()` → `activate(entry)`，用 `NSRunningApplication` 断言实例数与进程号。结果：点击后 `isVisible` 由 `true` 变 `false`（自动收起），未运行时启动出 1 个实例（PID 23014），再次点击后仍是同 1 个实例、同一 PID（激活而非新开）。
- **图标缓存无碰撞**：对 108 个缓存文件做 md5，无重复内容。截图中「妙手」与 `CatPawAI` 图标相同，核实为同一厂商的两款应用共用了品牌图形（两个文件哈希与字节数均不同），不是缓存串号。
- **冷缓存不阻塞唤起**：把 `icons/` 整个移走后重测，108 个图标全部在后台重新生成且均为合法 256×256 PNG；那次 496 ms 的冷扫描期间唤起覆盖层仍只要 21.9 ms。

## 未覆盖 / 留给后续切片

- **多屏切换未实测**：本机只有一块屏幕。窗口复用后新增了 `setFrame` 搬运逻辑（`preparedWindow` 在目标屏与当前 frame 不同时移动窗口），单屏下该分支不会被触发，需在有第二块屏的机器上验证。
- **新装应用不会立刻出现**：快照只在启动时与每次唤起时刷新。装完应用后需重新唤起一次覆盖层才能看到它——这与 ticket 014 的目标（FSEvents 触发、无需重启）不冲突，014 会补上增量触发。
- **应用清单变化时会重建视图树**，若覆盖层正处于打开状态，理论上可能有闪烁。ticket 014 的验收标准里明确要求处理这一点。
