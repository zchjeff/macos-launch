# FSEvents 增量同步与失效标记

**Blocked by**: 005, 011

**状态**：已完成（2026-09-26）

## 目标

新装的应用下次唤起覆盖层就能在「未分类」里看到；被删除的应用在控制台里标记为「失效」，覆盖层里不再出现。不需要重启 AppBox。

## 涉及层

- [x] 数据层：变更扫描后刷新 `lastKnownPath`（字段本身在 011 已落盘，本切片打通写入时机与只写已跟踪应用的范围）
- [x] 逻辑层：`Watching` 端口 + `FSEventsWatcher`；`LibrarySync` 负责合并窗口与分发；失效判定沿用 011 的「算出来」逻辑
- [x] UI层：变更后覆盖层原地换内容、控制台开着时当场更新（失效列表的呈现是 011 的产物）
- [x] 测试：假 `Watching` 手动触发变更，断言快照与失效标记（+8 个，158 → 166，26 → 27 个 suite）

## 验收标准

- [x] 监听 `/Applications`、`/System/Applications`、`~/Applications` 的目录变化
- [x] 新装一个应用到 `/Applications` 后，下次唤起覆盖层即能在「未分类」中看到它，无需重启 AppBox
- [x] 删除一个已分组的应用后，控制台出现「失效」条目，覆盖层不再显示它
- [x] 应用被**移动位置**（如 `/Applications` → `~/Applications`）后，不被标记失效，配置完整保留，仍能正常启动
- [x] 外接卷未挂载导致应用暂时不可见时，标记为失效而非删除配置（配置永不静默丢失）
- [x] `lastKnownPath` 在每次成功扫描后刷新
- [x] 目录变更后快照刷新不应造成覆盖层可见的闪烁（窗口 id 前后不变，见图与「验证」）
- [x] 连续快速变更（如一次性拖入 20 个应用）不造成重复扫描风暴（20 个新增 = 1 次 settle，20 个删除 = 1 次 settle）
- [x] 单元测试：假 `Watching` 触发「新增」、「删除」、「移动」三类事件，断言快照与失效标记

## `Watching` 端口刻意保持「哑」

端口只有 `start(onChange:)` / `stop()`，**不做任何合并**——底层来一帧就往上报一次。合并、分发、扫描全在 `LibrarySync` 里，那里不碰 FSEvents，可以拿假监听器单独测出「十个事件只扫一次盘」这种断言。

`FSEventsWatcher` 因此薄得只剩翻译：`FSEventStreamCreate` → `SetDispatchQueue` → `Start`，回调闭包揣着一个 `Unmanaged<CallbackBox>` 裸指针（FSEvents 不给捕获上下文），`stop` 里按 `Invalidate` → `Release` → `box.release()` 的顺序配对掉 `passRetained`——顺序不能反，反了就有回调落在一块已经释放的内存上。

监听路径**允许不存在**：`~/Applications` 在不少机器上本来就没有。这条是实测出来的，不是照文档推的——`/tmp` 下的探针拿不到事件（`/tmp` 是 `→ /private/tmp` 的符号链接），换成 `$HOME` 下一个不存在的目录反而拿到了：目录被创建之后事件照报。所以不需要「等目录出现再挂监听」这种补丁。

## 固定窗口，不是防抖

事件进来开一个窗口（默认 500ms），窗口里的后续事件**直接吸收**，窗口不因此延长。到期 settle：重扫一遍，把快照发出去。

不延长是关键的差别。防抖在持续写入时会永远不刷——往 `/Applications` 拷一个 2GB 的应用包，FSEvents 会一直报事件，界面就一直停在旧状态。固定窗口的代价是「拷到一半时可能刷出一个只有半个应用包的中间态」，而那个中间态下一次窗口就会自己修好；一直不刷则永远不会自己修好。

`0.5s` 之上还有 FSEvents 自己的 `latency`（也取 0.5s，理由是「装/删/移动」都是低频操作，半秒延迟换掉一串连珠炮划算），两者相加是一个变更从落盘到界面刷新的上限，约一秒。这条写进了 `FSEventsWatcher` 和 `LibrarySync.init` 的注释。

## 一次扫描，一份快照，所有人共用

`settle` 只调一次 `service.snapshot(recordingPaths: true)`，把**同一个** `LibrarySnapshot` 分发给所有订阅者。各订阅者各自重扫是不行的：中间隔着一个正在搬动的应用包时，覆盖层和控制台会各自看到一份数据，用户就会看见「控制台说失效了、覆盖层还在」。

`recordingPaths: true` 顺手办第二件事——把扫到的位置写进配置里**已经有条目**的应用。位置线索只管已跟踪的应用（108 个全记一遍就是凭空多出 100 多条记录），但它是「移动」和「删除」判不开时唯一的依据（ADR-0003）：路径没了、bundleID 还在别处出现，就是搬家，配置原样保留、`lastKnownPath` 更新；bundleID 整个不见了，才是失效。

## 停下来的语义：连窗口里那次也作废

`stop()` 递增一个 `generation`，settle 开场先对一遍代数，对不上就直接返回。少了这一步，`stop()` 之后那次已经排进 `Task.sleep` 的扫描照样会落地——测试 `stopCancelsPendingAndFutureChanges` 就是钉这个的（事件已进来、窗口没到头时停掉，断言一份快照都不该有）。

还有一道闸：`handlers` 为空直接返回，**没人订阅就不扫盘**。AppBox 的两个订阅者（覆盖层、控制台）都在 AppDelegate 里挂着，所以现实中不会空；但把「要么有人要，要么不干活」写成代码里的显式分支，比靠调用方的自觉可靠。

## 覆盖层原地换内容，窗口自始至终是同一个

`OverlayController` 里原来那次算完就丢的 `render(_:)` 升成了 `apply(_:)`，并多留了一份 `latestSnapshot`：

- `latestSnapshot` 是最近算出来的那份，`renderedSnapshot` 是当前视图树里那份。窗口还没建的时候只有前者存在——首屏因此不再是一张空网格再等后台填上，而是预热好的内容直接出（`makeWindow` 里用 `latestSnapshot ?? LibrarySnapshot(groups: [])`，并同步把 `renderedSnapshot` 设上，免得紧接着的那次后台校准白重建一次树）。
- `apply` 仍然只在快照**真的变了**的时候重建视图树。图标补全、`lastKnownPath` 刷新这类变化不影响画面，给 `rootView` 赋值却会重跑整棵 SwiftUI 树。

覆盖层这条路上一个字节都不写盘（017 的硬指标）：`refresh()` 走的是 `service.snapshot()`，不带 `recordingPaths`。写盘只发生在 `LibrarySync` 那条路上，而它挂的是「磁盘真的变了」。

## 控制台只在窗口开着时更新

`ConsoleWindowController.apply(_:)` 先看一眼 `window?.isVisible`。关着的时候模型更新了也没人看，而下次 `show()` 本来就会 `refresh()` 重读一遍，那时候读到的只会更新。

## 验证

**代码侧**：166 个测试通过（27 个 suite）。本切片新增 8 个，覆盖：变更后重扫并分发、新装应用落进「未分类」、删除后进失效且配置一条不丢、移动后不失效并按新路径启动（含 `lastKnownPath` 刷新）、十个事件只扫一次盘且两个订阅者拿到同一份快照、窗口过后再变更还会再刷、`stop()` 连窗口里未落地的那次也作废、没人订阅就不扫盘。

**真机侧**（用探针应用 `/Applications/0-探针.app` 做增删，日志走临时文件，验完全部回退）：

- 覆盖层开着时删掉探针应用：`settle` 在变更后 1.4 秒落地，`overlay.apply` 打出的窗口 id 与删除前**是同一个**（6049）。前后两张截图上，「0-探针」的方块消失、其余方块原地回流，没有整窗重建、没有闪白。
- 控制台（`open` 打开，之后零交互）：删探针后侧栏计数「未分类 108 个应用」+「维护 / 失效应用 1」；把探针放回去，计数自己变成「未分类 109 个应用」、失效分组整段消失。全程没人碰过控制台。
- 节流：一秒内创建 20 个应用 → 只有 1 次 settle；一秒内删掉这 20 个 → 也只有 1 次 settle。
- FSEvents 对**不存在**的目录同样有效（上面「端口」一节说的那个实测）。

## 手工验证清单（需要人手）

自动化查不到的是真实操作的时序，这几条得真做一遍：

1. 从 Finder 往 `/Applications` 拖一个应用（大一点的最好）：如果覆盖层当时开着，它应在约一秒内自己多出这个应用，且画面不闪
2. 拷贝一个几百 MB 的应用包，拷到一半时看覆盖层/控制台——应当在拷贝过程中就刷过一次（显示可能不完整），拷完再刷成最终样子；**不该**等到拷完才第一次刷新（那是防抖的行为）
3. 把一个已分组的应用拖进废纸篓：控制台当场出现「失效」条目，覆盖层里它消失
4. 把它从废纸篓拖回 `/Applications`：失效条目自己消失，设置（别名/分组/隐藏）全都还在
5. 挂上一个 DMG 或外接卷、把里面的应用加到分组，然后卸载/拔掉：应用变失效而非配置消失；重新挂上后自己恢复

## 备注

- 判定「移动」而非「删除+新增」的依据是 bundleID 相同、路径不同（ADR-0003），本切片把这条线索的**刷新时机**接上了：只有 `LibrarySync` 那条路会写 `lastKnownPath`
- 本切片只加「增量触发」与「失效判定」；应用扫描本身在 003 已完成，失效列表的 UI 与手动清理在 011 已完成
- 只有「动过设置的应用」才会进失效列表——没动过的应用消失就是彻底消失，因为它本来就没有设置可清理（011 的既定范围）
- FSEvents 只订阅目录级事件、不打开 `.fileEvents`：拖一个应用包进来会上报上百个文件级事件，而目录级的只有一条
