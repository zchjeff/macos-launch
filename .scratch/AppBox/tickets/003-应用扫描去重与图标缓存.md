# 应用扫描、去重与图标缓存

**Blocked by**: 001

## 目标

AppBox 能列出一份准确的应用清单：每个应用有显示名、bundleID、最近已知路径、类别、以及已缓存到磁盘的图标。验证方式是一条调试命令打印清单 + 单元测试。

**这是唯一刻意不含 UI 的切片。** 扫描与去重是最容易出错、最值得单测覆盖的部分，先在一个不牵扯窗口的地方做扎实。验证出口是调试命令，不是界面。

**状态**：已完成（2026-09-26）

## 涉及层

- [x] 数据层：`AppRecord` 模型（bundleID 主键、最近已知路径、显示名、类别、图标缓存路径）
- [x] 逻辑层：`AppScanner`（FileManager 实现）；Info.plist 解析；bundleID 去重与优先级；`IconRendering` 端口 + 图标磁盘缓存
- [x] UI层：无（提供一条调试命令打印扫描结果）
- [x] 测试：真实临时目录 fixture（`AppTree`），覆盖全部边界

## 验收标准

- [x] 扫描 `/Applications`、`/System/Applications`、`~/Applications` 及其**一级子目录**
- [x] 忽略应用包内部的嵌套 `.app`（如 `X.app/Contents/...`），不把 Helper 当应用
- [x] 解析 `Info.plist` 得到 `CFBundleIdentifier`、`CFBundleName`、`CFBundleDisplayName`、`LSApplicationCategoryType`
- [x] bundleID 缺失时回退用绝对路径作为主键
- [x] 同一 bundleID 出现多个副本时只保留一个，优先级 `/Applications` > `/System/Applications` > `~/Applications`
- [x] 单元测试覆盖：无 bundleID、重复 bundleID、嵌套 `.app`、`Info.plist` 损坏或缺失、`CFBundleName` 缺失时回退用文件名
- [x] 图标提取成功并缓存到 `~/Library/Application Support/AppBox/icons/`，缓存文件按 bundleID + 应用包修改时间失效
- [x] 二次扫描时命中缓存，不重新提取
- [x] 调试命令打印出的清单与访达中实际可见的应用一致，本机约 107 个 → **实际 108 个**
- [x] 首次全量扫描耗时 < 1 秒（spec H2）→ **0.058s**

## 验证方式与证据

调试命令：`AppBox --scan`（直接跑二进制，stdout 才接得到）。

### 清单条数的独立核对

不能只信自己的扫描器，所以用 `find` + `plutil` 另算了一遍（null 分隔处理带空格的路径）：

| 目录 | 根下 `.app` | 一级子目录内 `.app` |
|---|---|---|
| `/Applications` | 40 | 4 |
| `/System/Applications` | 46 | 19 |
| `~/Applications` | 0 | 0 |

原始合计 109 个包，去重后 108 —— 与扫描器输出**一致**。差的那一个是：

```
io.github.openconnect.openconnect-gui
    /Applications/OpenConnect-GUI.app
    /Applications/OpenConnect-GUI.app/OpenConnect-GUI.app   ← 应用包套应用包
```

即"不进入 `.app` 内部"这条规则在真机上确实生效了（内层那个从未被扫到）。

任务描述里写的"约 107 个"是拆分任务时的估值，实测 108，差异来自安装变化，不是漏扫或重复。

### 性能

| 场景 | 耗时 |
|---|---|
| 全量扫描（不含图标） | 0.058s |
| 图标**冷**缓存（渲染 108 个） | 0.537s |
| 图标**热**缓存（全部命中） | 0.012s |

缓存命中带来约 45× 提速，命中路径确实没有重新渲染。缓存目录 108 个文件、合计 4.9 MB。

## 实施中偏离原计划的地方

- **没有做 `AppScanning` 端口，`AppScanner` 是具体类型**。任务描述要求"`AppScanning` 端口 + FileManager 实现"以及"`AppScanning` 的假实现"。实际做下来，扫描这件事**只有一种实现**，测试要的也是真实文件系统行为（`Info.plist` 解析、目录遍历、嵌套规则），假实现只能验证假实现自己。凭空立一个只有一个实现、且没有任何假实现的协议是投机性抽象，所以去掉了。
  真正需要端口的是**图标渲染**——它必须碰 AppKit，而缓存逻辑（命中/失效/写盘）不该被 AppKit 拖进 UI 运行时。`IconRendering` 协议因此保留，测试里配 `FakeIconRenderer`（还兼作调用计数器，用来断言"命中缓存时不再渲染"）。
- **图标降采样到 256×256**。`NSWorkspace` 给的图标是 1024×1024，直接存 PNG 单个约 1.5 MB —— 108 个应用就是 **160 MB** 缓存，与 ADR-0005"图标缓存要轻量"的意图相悖。改为画进 256×256 的位图再编码，单文件降到约 45 KB（合计 4.9 MB）。覆盖层最大的方块在 2x 屏上也就 200 像素出头，256 够用。
- **去重排序改成全序**。最初只按"目录优先级"排序，于是同一个扫描根里出现两份时，胜者取决于 `contentsOfDirectory` 的返回顺序，会在两次扫描之间抖动（表现为图标和路径莫名切换）。测试抓到了这一点，补上"路径更浅优先 → 路径字典序"作为确定性决胜条件。
- **`AppScanner` 不注入 `FileManager`**。原本想注入以便测试，但 `FileManager` 不是 `Sendable`，存成属性会让 `AppScanner` 无法满足 `Sendable`。测试本来就用真实临时目录，注入没有换来任何东西，直接去掉。
- **进程入口从 `@main struct AppBoxApp` 改为 `@main enum EntryPoint`**。`--scan` 需要在 SwiftUI 启动之前返回，否则 `WindowGroup` 会先闪一下窗口。抽一层 `EntryPoint` 调 `AppBoxApp.main()` 是最干净的做法（在 `AppBoxApp` 内部重写 `static func main()` 会递归调到自己）。

## 真机上遇到的、值得记住的样本

- **`/Applications/AnyConnect.app` 没有 `Contents/`**。它是一个"包装型" bundle：结构是 `AnyConnect.app/Wrapper/AnyConnect.app` 加一个 `WrappedBundle` 软链，真正的 `Info.plist` 在内层。所以外层读不到任何元数据，主键退化成路径、显示名退化成文件名 —— 这条回退逻辑在真机上真的被用到了，不是纸上谈兵。同时也意味着内层那个真实应用不会被重复扫进来。
- **`/Applications/Cisco/Cisco Secure Client - Socket Filter.app` 被列进来了**。它是 Cisco 的 socket filter（系统扩展宿主），用户点不开。但它确实是一个位于一级子目录下的 `.app` 包，访达里也看得见，按本切片的规则就该收进来。要不要按"能否启动"过滤，本切片没有任何验收标准支持，硬编码一份排除名单也不合适 —— 留到后续切片按需要再说。

## 备注

- 图标缓存与配置文件物理分离，保证配置文件始终轻量（ADR-0005）
- 此切片只做"扫描 + 缓存"，不做"与配置合并"，也还没有「失效」概念——那些在 005 / 014 引入
